Architecture

Why 5 experimental configurations (RULES_ONLY → FULL_SYSTEM)?
The thesis question is "does adding LLM / RAG / validation to a fraud detection pipeline provide measurable value over purely rule-based or ML-based detection?" Testing isolated layers answers the how much question: each config adds exactly one stage relative to the previous, so the F1 / CAKR deltas attribute cleanly to that layer alone.
Considered: only RULES_ONLY + FULL_SYSTEM (simpler, but can't attribute which component drives the gain); continuous ablation over N layers (richer but much longer wall-clock).
Trade-off: 5 configs × k-fold = 5× training + 5× detection cost. Mitigated by running configs back-to-back using the same feature computation (done once).
Why Spring Boot + clean architecture instead of a notebook?
The thesis examines a system, not a model. Reproducibility, observability, concurrency, database persistence, and a user-facing demo all matter more than training a single best model. Spring Boot gives these for free; notebooks don't.
Why Java 25 with virtual threads rather than Python asyncio?
The hot paths are a mix of CPU-bound ML inference and I/O-bound LLM calls. Virtual threads (stable since Java 21, now on Java 25) let the same code block on I/O without exhausting a thread pool — ideal for the ~100-concurrent LLM calls a full CAKR evaluation triggers.

Data

Why PaySim as the primary dataset?
PaySim is a published, citable, synthetic mobile-money dataset with a realistic fraud base rate (~0.13%), real-world typologies (TRANSFER, CASH_OUT structuring), and 6.3M rows — large enough that performance claims are meaningful, small enough to run a full benchmark overnight.
Why temporal train/test split, not random?
Fraud is a time-series phenomenon — fraudsters adapt. A random split lets features computed over sliding windows "peek into the future" during training, inflating metrics (audit finding A-5). The temporal cutoff at the 80th-percentile timestamp ensures training rows strictly precede test rows.
Why PostgreSQL + pgvector instead of a dedicated vector DB?
Keeping fraud-pattern embeddings in the same database as transaction records lets RAG retrieval, detection, and analytics run inside one transactional system. pgvector's HNSW index hits <10 ms for top-k=5 on thousands of patterns — within 2× of FAISS / Pinecone at this scale, without the operational complexity.

Machine Learning

Why Random Forest + XGBoost ensemble?
Random Forest is bagging (variance reduction); XGBoost is boosting (bias reduction). They make different errors — combining them via higher-probability-wins gives better recall on the rare fraud class without sacrificing precision. RF also provides a stable baseline when the XGBoost JNI library is unavailable.
Why parallel RF mini-forests (4×25 trees) instead of one 100-tree forest?
Tribuo's RandomForestTrainer builds trees sequentially — no internal parallelism. Splitting 100 trees into 4 independent mini-forests on 4 threads gives ~4× wall-clock speed-up. Inference averages probabilities across mini-forests — mathematically equivalent to the full forest's soft-vote output.
Why reservoir sampling for legit training rows?
PaySim has ~0.13% fraud rate. Training on the full 6.3M rows wastes hours on obvious legit rows. Reservoir sampling keeps all ~8,500 fraud rows + a uniformly random sample of 200k legit rows — still imbalanced enough to test the model's handling of rare classes, 30× faster.

LLM

Why abstract behind Spring AI's ChatClient?
Writing directly against Anthropic's SDK or Ollama's would lock the codebase to one vendor. Spring AI gives one interface that works for Ollama (local default), Anthropic, OpenAI, and DeepSeek — provider switch is a Settings-UI click, which the "compare two judge LLMs" experiment needs.
Why CAKR (Completeness, Actionability, Knowledge, Regulatory)?
Generic quality metrics (BLEU, ROUGE) measure surface similarity to a reference — pointless when there's no gold-standard explanation. CAKR scores what a compliance analyst actually cares about: does the explanation reference the right signals, suggest concrete actions, use real fraud typologies, and cite applicable regulations.
Why store failed CAKR scores as NULL (not 0.0)?
The CAKR scale is [1, 5]. Storing a scoring failure as 0 puts it outside the scale and silently depresses AVG() in SQL (audit finding A-3). NULL is semantic: "no score" — SQL AVG skips it, so reported means reflect actually evaluated explanations.
Why a local HallucinationValidator in addition to CAKR?
An LLM judge gives a quality score but can miss concrete factual errors (wrong amount, invented account ID). The local validator performs deterministic cross-checks against the source transaction — cheap, reproducible, catches things LLMs don't.

Evaluation

Why k-fold cross-validation?
A single 80/20 split's metrics depend on which 20% we picked. k-fold (typically k=5) runs k independent splits and reports mean ± stddev — makes the reported F1 / CAKR numbers defensible rather than a single point estimate.
Why F1 as the headline detection metric?
Fraud is severely imbalanced (~0.13%). Accuracy is meaningless — a model that predicts "not fraud" for everything scores 99.87% accuracy. F1 balances precision (don't flood analysts with false alarms) against recall (don't let real fraud slip through).

Security

Why AES-256-GCM for LLM API key storage?
Authenticated encryption — catches tampering, not just confidentiality. 256-bit key is NIST-recommended; GCM uses a 12-byte random IV per encryption. Key material zeroed from heap after use (ApiKeyEncryptor).
Why Liquibase with ddl-auto: validate?
Liquibase changelogs are the single source of truth for schema. Hibernate's update mode can drift silently from what's checked into git. validate forces every deploy to match the declared schema exactly.

Performance

Why PostgreSQL COPY instead of Hibernate saveAll?
COPY streams rows directly to the storage engine, bypassing query parsing + planning. ~10-50× faster than Hibernate's batched INSERTs on 6M-row imports. Fallback path uses per-row REQUIRES_NEW transactions so one bad row doesn't nuke the batch.
Why bulk SQL with window functions for feature engineering?
Per-row feature computation requires 3+ DB round-trips per transaction. For 6.3M rows that's 19M queries — hours. A single bulk INSERT-SELECT with RANGE BETWEEN INTERVAL '24 hours' PRECEDING windows over PARTITION BY sender computes everything in one pass — ~1-3 minutes with parallel-worker GUC tuning.
Why polling for job status, not WebSocket / SSE?
Single-user thesis deployment — the throughput + latency benefits of push don't manifest. Polling is transparently debuggable (curl the status endpoint), requires no proxy-buffering workarounds, and FG.pollJob keeps the implementation to one place.
