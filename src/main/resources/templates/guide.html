What is FinGuard?

FinGuard is an LLM-augmented transaction anomaly detection system. It combines rule-based checks, machine learning models, and large language model explanations to detect and explain potentially fraudulent financial transactions.

System Architecture
Ingestion Layer

Imports PaySim CSV datasets, parses and validates rows, computes engineered features (z-scores, velocity, diversity metrics).

Detection Pipeline

Configurable chain: rule-based threshold checks, Tribuo ML models (Random Forest + XGBoost), alert generation with risk scores.

Explanation Engine

LLM-generated explanations with optional RAG context from a fraud pattern knowledge base. Evaluated via CAKR scoring.

Detection Configurations

Each detection run uses one of these pipeline configurations:

Config Rules ML LLM RAG Description
RULES_ONLY Threshold-based detection only. No ML or AI models needed.
ML_ONLY ML classification only. Requires trained models.
ML_LLM_DIRECT ML detection + direct LLM explanation (no knowledge base).
ML_LLM_RAG ML detection + RAG-augmented LLM explanation.
FULL_SYSTEM All stages combined. Full pipeline.

Step 1: Import Transaction Data

Navigate to Data Ingestion to import transaction datasets into the system.

Test Data

A small test dataset is included at src/main/resources/data/test-transactions.csv with sample PaySim transactions including fraud cases for TRANSFER and CASH_OUT types.

For the full dataset, download PaySim from Kaggle (~6.3 million rows, ~500 MB).

Expected CSV Format
step,type,amount,nameOrig,oldbalanceOrg,newbalanceOrig,nameDest,oldbalanceDest,newbalanceDest,isFraud,isFlaggedFraud
Import Options
Upload CSV

Upload the CSV file directly from your browser. Best for files up to ~200 MB.

Server Path

Specify a file path on the server. Best for large datasets already on the filesystem.

Compute Features

After importing, click "Compute Features" on the same page. This computes engineered features for all transactions that don't have them yet:

  • Amount z-score — how unusual the amount is relative to the sender's history
  • Transaction velocity — frequency of transactions in 1h and 24h windows
  • Receiver diversity — number of unique recipients for the sender
  • Balance change ratios — proportional changes in origin/destination balances
Features must be computed before training ML models or running any ML-based detection config.
Step 2: Train ML Models

Navigate to ML Models to train and manage the detection models.

Available Models
Random Forest

Ensemble of decision trees. Good baseline with interpretable feature importances.

XGBoost

Gradient-boosted trees. Typically higher accuracy for tabular fraud detection.

Steps
  1. Click "Train Models" — trains both models on all transactions with features. The fraud label from the dataset is used as the training target.
  2. Wait for training to complete. Status will show "Models available" when done.
  3. If the application restarts, click "Load Models" to reload previously trained model files from disk.
Training requires computed features. If you see zero features, go back to Ingestion and run "Compute Features" first.
Step 3: Seed the Knowledge Base

Navigate to Knowledge Base to populate the fraud pattern database.

What is the Knowledge Base?

The knowledge base stores known fraud patterns (e.g., "structuring", "account takeover", "money mule") as vector embeddings in PostgreSQL with pgvector. When the detection pipeline generates LLM explanations in RAG mode, it retrieves the most relevant patterns to provide rich context to the LLM, improving explanation quality.

pgvector — How RAG Actually Works

pgvector is a PostgreSQL extension that stores high-dimensional vectors and lets you search them by cosine / L2 / inner-product similarity. FinGuard uses it as its Retrieval-Augmented Generation (RAG) backing store.

  1. Table — vector_store (columns: id UUID, content TEXT, metadata JSONB, embedding VECTOR(768)).
  2. Index — HNSW on embedding with cosine distance; sub-millisecond top-K lookup up to millions of rows.
  3. Populated by FraudPatternSeeder — for every row in the fraud_patterns table, the pattern title + description is embedded via nomic-embed-text (768 dimensions) and inserted.
  4. Queried by RAGContextService.retrieveContext() whenever an alert needs an LLM explanation in ML_LLM_RAG or FULL_SYSTEM config: the alert's signal text is embedded, the topK = 5 most similar patterns are fetched, and they are injected into the LLM prompt as "here is what known fraud looks like — is this alert similar?".
  5. Tunable — finguard.explanation.max-rag-results in application.yml. Bigger = richer context but slower/costlier LLM calls.

Without pgvector seeded, ML_LLM_RAG degenerates to ML_LLM_DIRECT: no retrieval means no retrieved context means the LLM gets the same prompt either way.

How to Seed
  1. Click "Seed Knowledge Base" on the Knowledge Base page.
  2. This inserts a curated set of fraud patterns and computes their vector embeddings via the configured embedding model.
  3. The patterns table will populate showing each pattern's name, category, and description.
The knowledge base is required for ML_LLM_RAG and FULL_SYSTEM configs. Not needed for RULES_ONLY, ML_ONLY, or ML_LLM_DIRECT.
Seeding requires a running Ollama instance (or configured embedding provider) to generate vector embeddings.
Step 4: Run the Detection Pipeline

Navigate to Run Detection to analyze transactions for anomalies.

How to Run
  1. Select a Detection Configuration from the dropdown (see Overview tab for comparison).
  2. Click "Run Detection" — the pipeline analyzes all unprocessed transactions.
  3. The system processes in batches and skips transactions that already have alerts for the selected config.
  4. When complete, the result panel shows how many alerts were created.

Async Execution

For large datasets, the pipeline can run asynchronously via the REST API:

POST /api/v1/detection/run/async?config=FULL_SYSTEM → returns jobId
GET /api/v1/detection/status/{jobId} → poll progress
Start with RULES_ONLY to verify your data pipeline works before moving to ML-based configs.
Step 5: Review Results & Export
Dashboard

The Dashboard provides a system-wide overview: total transactions, alerts created, fraud detection rate, alert breakdowns by status and config, CAKR quality scores, and experiment summaries.

Alerts

Alerts shows every alert generated by the pipeline. Filter by status (NEW, REVIEWED, CONFIRMED_FRAUD, FALSE_POSITIVE) or by detection config.

Click an alert to see full details: the original transaction, ML risk score, feature importances, triggered rules, and all LLM explanations. You can update the alert status from the detail page.

Explanations

Explanations lists all LLM-generated explanations with quality metrics: CAKR scores (Completeness, Correctness, Actionability, Regulatory), token counts, latency, and hallucination detection results.

CSV Export

Export results for external analysis via the REST API:

GET /api/v1/export/alerts → all alerts as CSV
GET /api/v1/export/alerts?config=FULL_SYSTEM → filter by config
GET /api/v1/export/experiments → experiment metrics as CSV
GET /api/v1/export/experiments?name=baseline → filter by name
Step 6: Run Experiments

Navigate to Evaluation to benchmark different detection configurations.

What Experiments Do

An experiment runs the detection pipeline with a specific configuration and records performance metrics: precision, recall, F1-score, processing time, and explanation quality (CAKR scores). This lets you compare how well different configs perform.

How to Run
  1. Enter an experiment name (e.g., "baseline-rules", "full-system-v1").
  2. Select a detection config from the dropdown.
  3. Optionally filter to a specific dataset source.
  4. Click "Run Experiment" and wait for completion.
  5. Results appear in the table below with all computed metrics.
Comparing Experiments

Use the "Compare" button for a side-by-side comparison of experiment runs. This is useful for evaluating the impact of adding RAG context, switching configs, or testing with different datasets.

Run at least one experiment per detection config to have meaningful comparison data for your thesis.
REST API Reference

The application exposes ~50 REST endpoints across ingestion, detection, evaluation, explanation, knowledge base, model training, data management, system, and LLM provider domains. Maintaining a hand-written list reliably is impractical — keep Swagger UI as the single source of truth:

Open Swagger UI Raw OpenAPI JSON Both require the app to be running.

Swagger UI lets you call every endpoint interactively from the browser — no curl needed. Click any endpoint, "Try it out", fill in parameters, click "Execute".
